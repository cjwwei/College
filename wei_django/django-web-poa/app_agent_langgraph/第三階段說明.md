# 第三階段說明：Custom LangGraph 自定義工作流

## 1. 第三階段的目標

第三階段的核心目標，是把原本偏向「預先包裝好的代理人」模式，改成一個**完全由我們自己掌控的 LangGraph 自定義狀態圖工作流**。這樣做的好處是：

- 可以清楚定義每一個節點的責任。
- 可以精準控制模型何時思考、何時呼叫工具、何時停止。
- 可以在每一步都加入 Console 輸出，方便除錯與觀察。
- 可以保留 Django Session 的對話記憶，讓整體問答具有上下文。

簡單來說，第三階段不再只是「AI 幫你回答問題」，而是讓 AI 變成一個**可觀察、可控制、可擴充**的分析流程引擎。

---

## 2. 第三階段使用到的主要元件

第三階段的實作主要由下列幾個部分組成：

### 2.1 `LangGraph StateGraph`
這是整個第三階段的核心。`StateGraph` 用來描述資料在不同節點之間的流動方式。每個節點都能讀取目前的狀態，並回傳新的狀態。

### 2.2 Gemini 3.1 模型
第三階段的 LLM 採用 `gemini-3.1-flash-lite`。它負責：

- 理解使用者問題。
- 判斷是否需要使用工具。
- 根據工具結果撰寫最終答案。

### 2.3 工具節點 `ToolNode`
第三階段沿用前一階段已經寫好的查詢工具，包含：

- `get_top_keywords`
- `get_top_persons`
- `get_keyword_correlation`
- `get_keyword_paragraphs`

這些工具被交給 LangGraph 使用，當模型決定要查資料時，就會由工具節點實際執行。

### 2.4 Django Session
前端輸入的每一輪對話，都會存進 Session 中，形成對話歷史。這讓第三階段具備上下文記憶，可以延續前文進行追問。

### 2.5 `views.py`
`views.py` 是前後端之間的控制入口，負責：

- 建立 Session 歷史。
- 接收使用者輸入。
- 呼叫 `run_custom_graph()`。
- 把回傳結果送回前端畫面。

---

## 3. 第三階段的整體架構

第三階段可以拆成兩層來看：

### 3.1 前端層
使用者在頁面中輸入問題，按下送出後，瀏覽器會送出 AJAX 請求到 Django view。

### 3.2 後端圖流程層
後端收到請求後，會把對話歷史與本次問題一起送進 LangGraph。LangGraph 再依照以下流程運作：

1. `agent_node` 先思考。
2. 如果模型決定要查資料，就會進入 `ToolNode`。
3. 工具執行完後，流程再回到 `agent_node`。
4. 若模型認為資料足夠，便產生最後答案並結束。

---

## 4. 第三階段的程式檔案分工

第三階段目前主要有這些關鍵檔案：

- `app_agent_langgraph/graph_core/graph.py`
- `app_agent_langgraph/graph_core/state.py`
- `app_agent_langgraph/views.py`
- `app_agent_langgraph/urls.py`
- `app_agent_langgraph/templates/app_agent_langgraph/chat.html`
- `app_agent_langgraph/config.py`

其中最重要的是 `graph.py`，因為真正決定流程的人就是它。

### 4.1 `state.py` 是在做什麼？

`state.py` 可以把它理解成「第三階段工作流的資料容器定義」。它不負責推理，也不負責查資料，它只是在定義：

- 這個圖流程裡面，狀態要長什麼樣子。
- 什麼資料可以在節點之間傳遞。
- 當節點回傳新資料時，要用什麼方式合併。

目前第三階段的 `GraphState` 很簡單，只有一個核心欄位：

- `messages`

這個欄位的型別是 `Annotated[list[BaseMessage], add_messages]`，意思是：

1. 這裡存放的是一串訊息。
2. 每當某個節點回傳新的 `messages`，LangGraph 不會把舊資料整包覆蓋掉。
3. 它會把新訊息「追加」到原本的對話裡。

所以你可以把 `state.py` 想成一個「對話記錄箱」。
所有節點都會共用這個箱子，並且把資訊放進去或從裡面讀出來。

如果沒有 `state.py`，LangGraph 就不知道你希望流程中傳遞什麼資料，也不知道要怎麼把各步驟的結果串起來。

### 4.2 `graph.py` 是在做什麼？

`graph.py` 才是第三階段真正的「流程控制中心」。如果說 `state.py` 是資料容器，那 `graph.py` 就是整條工作流的施工圖與執行規則。

它主要做了這幾件事：

1. 先初始化 Gemini 模型。
2. 把工具綁到模型上。
3. 定義 `agent_node`，讓模型先思考。
4. 定義 `should_continue()`，判斷接下來要不要去工具節點。
5. 建立 `ToolNode`，負責真的去執行查詢工具。
6. 把節點和邊串成 `StateGraph`。
7. 編譯成可以執行的 `app_graph`。
8. 提供 `run_custom_graph()` 給 Django view 呼叫。

你可以把 `graph.py` 理解成一個完整的 AI 工作流：

- `agent_node` = 先想一想
- `should_continue()` = 判斷下一步
- `action` / `ToolNode` = 實際去查資料
- `agent_node` 再跑一次 = 把資料整理成最終答案

因此，第三階段真正的重點不是單一函式，而是 `graph.py` 裡這整套「思考 -> 行動 -> 再思考 -> 結束」的設計。

## 5. 第三階段模型開發的步驟

下面是第三階段完整的開發步驟。

### 步驟 1：建立 Graph 狀態
先在 `state.py` 定義 `GraphState`，目前的核心狀態是：

- `messages`

這個欄位會保存對話訊息，並透過 `add_messages` 逐步累加，而不是每次覆蓋。

這代表 AI 可以看到：

- 使用者前面問過什麼。
- AI 前面回答過什麼。
- 工具回傳過什麼。

### 步驟 2：初始化 Gemini 模型
在 `graph.py` 中先讀取 `config.py` 裡的：

- `MODEL_NAME`
- `GEMINI_API_KEY`
- `SYSTEM_PROMPT`

然後建立 `ChatGoogleGenerativeAI`。

這樣做的好處是，模型名稱以後只要改 `config.py` 一個地方就行，不需要到處找硬編碼字串。

### 步驟 3：綁定工具
把查詢工具整理成 `tools` 清單，並用 `llm.bind_tools(tools)` 綁到模型上。

這一步的意義是：

- 讓模型知道自己可以用哪些工具。
- 讓模型有能力在回答前先呼叫工具查資料。

### 步驟 4：建立 `agent_node`
`agent_node` 是第三階段裡的「思考節點」。

它的工作是：

1. 讀取目前所有 messages。
2. 在每一輪對話前加入系統提示詞 `SYSTEM_PROMPT`。
3. 把資料送給模型。
4. 觀察模型是否產生 `tool_calls`。

如果模型有 `tool_calls`，代表它決定要先查資料；如果沒有，代表它可以直接回答。

### 步驟 5：建立 `should_continue()` 路由判斷
這個函式負責判斷下一步要走哪裡。

判斷方式很簡單：

- 如果最後一則 message 有 `tool_calls`，就走到工具節點。
- 如果沒有 `tool_calls`，就直接結束。

這就是第三階段最重要的控制邏輯之一。

### 步驟 6：建立 `ToolNode`
`ToolNode(tools)` 是 LangGraph 提供的工具執行節點。

當 `agent_node` 決定要查資料時，流程就會進入這裡，由工具實際查詢資料庫或執行對應邏輯。

### 步驟 7：組裝 `StateGraph`
第三階段的圖結構如下：

- `START -> agent`
- `agent -> action`（當模型需要工具時）
- `action -> agent`（工具執行完後回到思考節點）
- `agent -> END`（當模型已經可以直接回答時）

這代表第三階段是一個典型的「思考 -> 行動 -> 再思考 -> 結束」的循環。

### 步驟 8：編譯成 `app_graph`
當圖形結構定義好後，使用 `workflow.compile()` 轉成真正可執行的物件。

這個 `app_graph` 就是後續 Django view 會直接呼叫的主體。

### 步驟 9：建立 `run_custom_graph()`
這是第三階段真正對外提供的入口函式。

它負責做這幾件事：

1. 接收使用者輸入。
2. 把歷史訊息從 Django Session 轉成 LangChain message 格式。
3. 把目前這次的使用者輸入加入 messages。
4. 執行 `app_graph.invoke()`。
5. 讀取最後的回答內容。
6. 把新的對話再寫回 Session。
7. 回傳給前端。

## 6. 第三階段整體運作流程

第三階段的完整流程如下：

### 6.1 使用者送出問題
使用者在 `chat.html` 輸入問題，透過 AJAX POST 請求送到 Django。

### 6.2 `views.py` 接收請求
`chat_view()` 會先確認 Session 是否存在 `custom_graph_history`。

如果沒有，就先建立空陣列，避免後續出錯。

### 6.3 把資料交給 `run_custom_graph()`
`views.py` 取得：

- 使用者這次輸入的文字
- 目前的對話歷史

然後把這兩個參數送進 `run_custom_graph()`。

### 6.4 進入 LangGraph
`run_custom_graph()` 會把歷史訊息轉換成：

- `HumanMessage`
- `AIMessage`

接著送進 `app_graph.invoke()`。

### 6.5 `agent_node` 開始思考
模型先看：

- 目前對話上下文是什麼
- 這次問題是否需要查資料
- 是否需要呼叫工具

### 6.6 若需要工具，就進入 `ToolNode`
如果模型認為應該查熱門關鍵字、人物、關聯度或新聞段落，就會進入工具節點。

### 6.7 工具回傳資料後再回到 `agent_node`
工具執行完後，資料會回到圖中，模型再進一步整合分析。

### 6.8 生成最終答案
當模型覺得資訊足夠時，就會生成最後回答。

這個回答會：

- 回到 Django view
- 更新 Session
- 回傳到前端聊天室

## 7. Console 輸出與除錯方式

第三階段目前有直接在程式中使用 `print()` 輸出執行訊息。

這些輸出會幫助你觀察：

- 使用者送了什麼問題
- `agent_node` 進入了幾次
- 模型是否要求使用工具
- `should_continue()` 判斷了什麼
- 最終是否完成回答

這種做法的優點是：

- 不需要額外設定開關。
- 直接簡單。
- 除錯時一眼就能看到流程。

## 8. 為什麼第三階段要改成 Custom Graph

第三階段之所以值得做，原因是它比預設的代理人模式更可控：

### 8.1 能明確知道流程怎麼走
每一個節點都由我們自己寫，所以你知道：

- 哪一步在思考
- 哪一步在查資料
- 哪一步在做判斷
- 哪一步在結束

### 8.2 比較容易擴充
之後如果你想加上：

- 寫作節點
- 摘要節點
- 資料清洗節點
- 判斷情緒節點

都可以直接新增節點與路由。

### 8.3 除錯更方便
如果某一步出問題，可以直接鎖定對應節點，而不是從黑盒式的 agent 裡面猜。

## 10. 一個簡單的實際例子

假設使用者輸入：

> 請幫我分析「台積電」與「張忠謀」這兩個詞的關聯度。

第三階段的執行過程會是：

1. 前端送出問題。
2. `views.py` 接到請求。
3. `run_custom_graph()` 把歷史對話與新問題打包。
4. `agent_node` 判斷這題需要查資料。
5. 模型請求工具。
6. 工具節點查出關聯度資料。
7. 資料回到模型。
8. 模型整合成最終回答。
9. 回應寫回 Session 並送回前端。

最終使用者看到的是一段自然語言分析結果，而不是原始資料庫查詢內容。

## 12. 核心 AI 概念解析

本 APP 實作了當前 AI 領域最前衛的幾個核心概念：

### 12.1 函數呼叫 (Function Calling) 與 工具使用 (Tool Use)
這是 Agent 的「手」。透過 `llm.bind_tools()`，我們賦予了模型操作外部系統的能力。模型不再只是「說」，而是能透過發出指令來「做」。

### 12.2 Agent (代理人) 架構
本專案利用 LangGraph 實作了具備自省能力的 Agent。它遵循 **ReAct 範式**：
- **Reason (推理)**：在 `agent_node` 決定策略。
- **Act (行動)**：在 `action` 節點執行工具。
- **Observe (觀察)**：讀取工具回傳結果，決定下一步。

### 12.3 Skill (技能) 的概念
在 Agent 的世界裡，每一個 Tool 都是一個獨立的 **Skill**。
- **原子技能**：如 `get_top_keywords` 是資料提取技能。
- **複合技能**：透過 **System Prompt** 定義的專業邏輯（如：不隨便猜測類別），其實就是一種「高階導引技能」。它將多個原子技能串聯，並賦予專家的判斷邏輯。

### 12.4 MCP (Model Context Protocol) 的思想
雖然本實作尚未導入正式的 MCP 協定，但其架構與 MCP 的精神不謀而合：**標準化模型與上下文資料的交互介面**。
透過定義明確的 State 與 Tool 介面，我們成功將「推理邏輯」與「資料獲取」解耦，這正是 MCP 想要解決的核心問題。

### 12.5 System Prompt 作為技能描述
`config.py` 中的 `SYSTEM_PROMPT` 不僅僅是文字，它是一份 **Agent 運作規範**。
它描述了：
1. **角色定位**：輿情分析專家。
2. **操作約束**：針對 category 的反問規則。
3. **輸出標準**：Markdown 格式要求。

這種將「專業行為規約」寫入 Prompt 的做法，本質上就是將 **「專家經驗」程式化為 AI 的一種內建 Skill**。

## 11. 第三階段的結論

第三階段的設計重點不只是「讓 AI 能回答」，而是讓 AI 具備：

- 可控的流程
- 可觀察的步驟
- 可擴充的節點
- 可追蹤的記憶

它是一個比較接近真正工作流引擎的 AI 架構，而不是單純的聊天機器人。

如果未來要持續升級，第三階段會是很好的基礎。
